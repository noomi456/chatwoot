# Application Boundary

## Purpose

Own ChatRing's customer- and agent-facing Community Edition application behavior while preserving the proven Chatwoot operational kernel.

## Ownership

- Rails-rendered login, onboarding, Super Admin, email, and layout surfaces.
- Supported CE application behavior and API compatibility.
- Child ownership for frontend runtime and branding helpers under `app/javascript/`.

## Local Contracts

- Customer-visible identity is ChatRing; internal Chatwoot model, route, event, and database contracts remain compatible.
- Phase 1 behavior remains the conventional Chatwoot conversation foundation. Phase 2 control-plane modules may extend it only through ChatRing-owned CE code; external extraction, retrieval and model systems remain replaceable dependencies and may not become conversation or delivery authorities.
- `ChatRing::Knowledge` owns provider-neutral evidence objects and knowledge-provider adapters. Providers return supporting evidence to the future Brain and never create Chatwoot Messages themselves.
- One `ChatRing::Workspace` maps one-to-one to a Chatwoot Account and owns one canonical business Knowledge Base shared by every Assistant and Inbox in that account. Knowledge ownership is never per Inbox.
- The administrator controls content only through Add, row-level Re-run, and Delete. No scheduled Firecrawl crawl/Monitor, user-visible publication/version workflow, or second Update Knowledge action may change the catalog.
- The Webpages input accepts either a complete website or one exact page. Complete websites use Firecrawl Map, pre-scrape filtering of operational, policy, Help/Docs, and Blog routes, and exact batch scrape of the remaining pages as one user Add command. Any excluded page can still be added explicitly through the exact-page input, which uses Firecrawl Scrape directly. An explicit row Re-run always scrapes that page with `maxAge: 0`.
- The Files input sends supported validated documents to Firecrawl Parse. Files and website pages converge into one account Training Materials catalog and one DocsGPT index; Q&A and Images remain later, separate knowledge views.
- DocsGPT is a private replaceable execution dependency. ChatRing uses scoped service authentication and one isolated provider source per hidden account index; provider-side answer Agents and legacy search API keys are not part of the retrieval contract.
- Production evidence must include a finite numeric provider score, score kind, rank, exact hidden-index binding, a verified provider chunk-content hash, canonical source URL and title, retrieved heading path, normalized page heading outline, safe source-derived CTA candidates, and retrieval configuration identity. Reject scoreless, non-finite, hash-mismatched, or off-manifest results and represent insufficient evidence as an empty typed outcome.
- Successful extraction updates that material snapshot and queues exactly one hidden replacement index from all active Training Materials. A manifest digest prevents duplicate builds and prevents an older build from replacing newer user changes.
- Delete tombstones the exact row immediately, so retrieval rejects it before provider cleanup. Re-run preserves the last active snapshot on extraction failure. Deleting the final row returns typed `insufficient_evidence`.
- Hidden provider-index snapshots are immutable and atomically swapped only after ingestion/provenance validation. Keep only the active index and a short-lived retired index; cleanup is an idempotent delayed Sidekiq job, not an hourly lifecycle/lease system.
- A nonterminal `AiTurn` pins its immutable Knowledge index. Provider cleanup is scheduled normally but defers itself while any received, eligible, running, awaiting-tool or ready-to-commit turn references that index; pin acquisition and the destructive recheck serialize on the Knowledge Base row.
- Account destruction must retain an independently executable provider tombstone before Workspace records cascade. Inbox destruction must not affect account knowledge.
- A ChatRing Assistant is an immutable, versioned role and security configuration. It is separate from Chatwoot's managed AgentBot identity, and every active Assistant AgentBot must be account-owned by the same Workspace Account.
- Basic Assistant administration uses one optimistic-locking mutable draft per Assistant and publishes only through immutable `AssistantVersion` snapshots. Mutations serialize in Account → Assistant → Draft/Connection order and recheck terminal archive state inside that boundary. New Assistants use the locked release model; an existing Assistant draft may preserve only its exact already-published historical model. Account-admin APIs must call the existing managed AgentBot provisioning, Inbox binding/drain/deactivation and archive services; they may project configuration health and existing turn/attempt/outcome failures, but may not become assignment, Conversation, Message, handoff or secret authority. Failure projections omit customer content, prompts, evidence excerpts and credentials. While the compile-time public-response gate is closed, new account-admin Inbox bindings fail closed server-side; existing bindings remain inspectable and may still be drained, disabled or archived.
- Inbox Assistant activation is versioned, serialized on the Chatwoot Inbox row, and fails closed when an external AgentBot, Dialogflow, Captain, another ChatRing Assistant, a competing native template outcome, or a public-response/ownership automation can own the response path. Automation creation/update/activation reciprocally rejects rules that conflict with an active ChatRing binding. Rebinding must drain and hand off conversations owned by the old managed AgentBot before activating the replacement. Managed ChatRing AgentBots are not exposed through external AgentBot CRUD or invalid Inbox assignment paths.
- In the current single-deployment architecture, the scoped Web Widget writer creates one minimal `NativeHandlingCompletion` only after its locked managed-binding recheck; synchronous template completion and native `AutomationRuleListener` completion then meet in that record. It is keyed to the trigger Message and stores only both completion timestamps, content-free native snapshots/effect provenance, release time and the resulting `AiTurn`; it owns no Conversation, Automation or responder state. The second native side releases at most one `AiTurn` under Inbox then Conversation locks without re-evaluating native rules or actions. The managed account-owned AgentBot remains the native owner and sender but has no public self-webhook, and the managed webhook route rejects requests in internal mode. Timestamped HMAC ingress and the conditional HTTP endpoint are inactive, isolated contracts for a future physically external runtime; that mode must use both boundaries end to end.
- Immediate `message_created` Automation coexistence is decided from the effects already produced by the native listener/action path. A public Automation Message/attachment or native status/owner/team change owns that trigger; label, priority and private-note-only effects may coexist. The pinned decision remains authoritative if a rule is later disabled or deleted. Only rules proven by native conditions to apply to incoming messages use this observed path; unconstrained message rules, indirect webhook actions and other native event types remain fail-closed conflicts.
- When the compile-time public-response gate is closed, the internal scheduling seam must not create or enqueue an `AiTurn`. A previously queued `received` turn that reaches its job after closure is terminally cancelled without inference or customer-visible mutation.
- Sales Core v1 is the current product boundary: one shared sales Brain, the text Business Knowledge Base, Inbox-owned phrase-triggered Playbooks, shared Tools governed by Inbox policy, Website Engagement starter pills, native actions/Automation coexistence, certified channels, human voice/calls and complete sales administration. AI Navigator, media-aware Knowledge, Sales Entities and Microsites are a later separately gated visual stage.
- The approved v1 channel order starts with Web Widget, then certifies Twilio SMS, Email, WhatsApp Cloud, Facebook Messenger and Instagram when each real provider path is configured. All reuse native channel ingress, Contact/ContactInbox, Conversation/Message, `SendReplyJob`, provider delivery and status semantics. Cloudflare RealtimeKit remains the native Website human-call seam; Twilio PSTN Voice is a separately audited CE capability because its current backend runtime is Enterprise-only and cannot be copied.
- `ChatRing::AiTurn` processing re-reads Chatwoot authority and builds one immutable in-memory `Brain::Invocation`: trusted Account/Inbox/Contact/Conversation/Message identifiers remain server-side, while the model projection omits Contact PII/private notes and preserves customer, human-agent, managed-AI, native-template, Automation and external-bot/system provenance. Empty audience/availability policies mean all visitors within native Inbox working hours; non-empty policies fail publication until their schemas exist. The persisted deadline is enforced before retrieval, inference, retry and final commit. The v2.2 Section 13 gates prove only the bounded native-lifecycle path; public AI remains compile-time disabled until the complete Sales Core v1 release gate in `docs/architecture/ChatRing_Complete_Production_Foundation_Direction.md` also passes on the exact deployed paths.
- The ChatRing Brain may assemble bounded public history, retrieve Assistant-scoped evidence, call an edition-neutral LLM adapter, and persist a typed decision plus attempts/evidence. It must not call Captain services, hold credentials in Assistant records, change Chatwoot ownership, or create a public Message.
- A Brain reply decision is valid only with accepted evidence IDs supplied in that turn. Insufficient evidence or provider exhaustion produces the configured abstain/handoff decision; the later final commit gate remains the only path to a customer-visible message.
- RubyLLM performs one bounded provider request per `AiTurnJob` attempt; ActiveJob is the only retry owner. Exhausted inference prepares and dispatches the configured native outcome. A failed outcome enqueue falls back to the same idempotent commit job inline, while the durable `ready_to_commit` state and explicit operator resume task cover a crash before dispatch without an hourly reconciler.
- Qualifying public incoming customer messages and public human replies use the shared Conversation serialization boundary for Inboxes with an active or draining ChatRing binding, with authoritative state rechecked inside the boundary. Conditional replies, native human takeover, handoffs and binding transitions use that same boundary while rechecking turn, binding, Assistant version, ownership, freshness, native-response outcome and idempotency before invoking ordinary Chatwoot behavior. Inboxes without a ChatRing binding retain upstream write behavior.
- Before adding any ChatRing lifecycle, transport, assignment, writer, handoff, retry or delivery mechanism, identify and extend the equivalent native Chatwoot service first. ChatRing-only components are permitted only for capabilities Chatwoot does not provide and remain subordinate to Chatwoot authority. The first-release serialization guard wraps only the approved Web Widget and dashboard public-reply writers; it is never a global `Message` callback.
- ChatRing records one durable idempotent customer-affecting commit per `AiTurn`, covering reply or handoff. Retries reuse its stable key and an already committed key returns the original result. The compile-time public-response gate remains authoritative until both the v2.2 full native-lifecycle suite and the complete Sales Core v1 production-foundation release gate pass.
- `ChatRing::AssistantSpike` exposes only the compile-time public-response and external-runtime gates. The deterministic spike responder is removed; no alternate responder may bypass the v2.2 production path and release gates.
- Do not import or mirror Enterprise implementations.
- Use installation configuration or the frontend branding helper for product identity instead of scattered hard-coded replacements.

## Work Guidance

- Prefer the smallest upstream-compatible CE patch.
- Keep customer-visible strings in the existing i18n/configuration paths where available.

## Verification

- Exercise login, onboarding, dashboard, inbox, widget, survey, and transactional email surfaces in the deployed image.
- Confirm API, webhook, WebSocket, and message-delivery contracts remain unchanged.
- For Phase 2A, prove account ownership and cross-tenant isolation; two-Inbox sharing; Website A plus Website B plus files; direct-page scrape; fresh row Re-run; immediate Delete; stale-index rejection; partial page success; truthful Training Materials state; real PDF/DOCX parsing; scored retrieval/abstention; authenticated provider calls; and idempotent obsolete-index cleanup.
- For the Assistant response loop, prove both native template/Automation completion orderings; actual benign label/priority/private-note coexistence; public reply/attachment and status/owner/team suppression; pinned decisions after rule mutation; no rule/action re-execution; v2.2 Section 13 precedence; internal scheduling; managed assignment/rebind/handoff; scoped serialization; failure fallback; idempotency; normal `SendReplyJob` delivery; non-managed channel regression; and identical persisted output in the Inbox and Classic Widget.
